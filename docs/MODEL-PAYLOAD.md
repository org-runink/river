# The encrypted model payload

> The model payload is one of the payloads a private medium can carry; the generic
> downstream payloads, the public/private split and air-gapped installs are in
> [PAYLOADS.md](PAYLOADS.md).

A Runink River Server install medium can carry the model set pinned in `models.lock`, so an
air-gapped machine installs with its models and needs no model store at enrollment. The
models travel **next to** the live image, never inside it, as one compressed and encrypted
payload at `/river-models` on the ISO. The installer unpacks it into its own natively
encrypted ZFS dataset, `<pool>/models`, and checks every file against `models.lock` before
anything uses it.

The payload is optional. Without it the medium is the same image as before, and the models
arrive at enrollment (`MODEL_STORE_URL`, [INSTALL.md](INSTALL.md#models-and-ci-runner)).

## At a glance

| | |
|---|---|
| Contents | Exactly the rows of `models.lock` (for the image being built): every file, nothing else |
| Pipeline | `tar` (lock order, fixed metadata) → `zstd -12` → AES-256-GCM in 4 MiB chunks → parts of 1900 MiB |
| Key | PBKDF2-HMAC-SHA256 (1,048,576 iterations, random 16-byte salt) of a passphrase chosen at build time |
| Passphrase | Generated by default (32 random bytes as 64 hex characters). **Never on the medium.** |
| On the ISO | `/river-models/MANIFEST` (plaintext) and `models.rmp.000`, `.001`, ... |
| On the node | `<pool>/models`, mounted at `/var/lib/core/models/shared`, encrypted under the pool's own key |
| Tool | `river-modelpack` (Go standard library, in `runink-installer`) and `zstd` (already on every image) |

## Why this design

The requirement is a medium that carries the models **compressed and encrypted**, without
adding packages to the image and without making the build need root.

**Chosen: an authenticated stream, then native ZFS encryption at rest.** The payload is
encrypted in user space with AES-256-GCM, so the build runs as an ordinary user and the
format is small enough to specify here. On the node, the files are written straight into a
dataset that inherits the pool's `aes-256-gcm` encryption root
([ENCRYPTION.md](ENCRYPTION.md)): from the first byte written they are sealed by the
install's own ZFS key, and the build passphrase protects nothing on the node after install.
Two keys, two jobs: the passphrase protects the medium in transit, the pool key protects the
node at rest.

Alternatives considered:

| Option | Why not |
|---|---|
| A ZFS raw send stream (`zfs send -w`) of an encrypted dataset, received into `<pool>/models` | Compressed and encrypted blocks would arrive as they are, which is attractive. But building it needs root and a ZFS kernel module on the build host whose feature flags the node must accept, the medium format becomes the OpenZFS on-disk format, and the receiving node still needs the build key (`zfs load-key`, then `zfs change-key -i`). It moves the problem, and adds a root step to the build. |
| A LUKS container image | Root and device-mapper on both sides, and `cryptsetup` would be a new package in the closure. |
| `gpg --symmetric` / `age` | `age` is not in the closure. `gpg` is, but its symmetric mode gives no per-chunk authentication while streaming, so a damaged medium is only detected at the end, after the data has been used. |
| Models inside the live squashfs | They would be in the image itself (against invariant 4), `20-clone-rootfs` would copy them onto every target's boot environment, and they would be unencrypted. |

## Security properties

- **Confidentiality of the medium.** Without the passphrase, the medium reveals the
  `MANIFEST` only: part sizes and hashes, the total size, and the sha256 of the lock the
  payload was built from. `models.lock` is public in this repository, so that hash tells
  which public model set is inside and nothing more.
- **Integrity.** Every 4 MiB chunk is authenticated. The nonce is a 7-byte random prefix, a
  32-bit chunk counter and a last-chunk flag (the STREAM construction), so reordering,
  dropping, repeating, truncating or extending chunks fails authentication, and the format
  and salt are bound in as associated data. Each part's size and sha256 are checked against
  the `MANIFEST` as it is read, which names a damaged part of the medium. Each extracted file
  must be a `models.lock` row, is written to a fresh file in an empty directory, and must
  match the row's size and sha256. The installer then re-checks the whole directory with
  `sha256sum -c` against `models.manifest` (generated from the same lock at build time).
  Any failure destroys `<pool>/models`: a node never keeps a partial or altered model set.
- **The passphrase.** Generated passphrases carry 256 bits, so the key derivation cost is
  irrelevant for them; for a chosen passphrase (at least 20 characters) PBKDF2 at 2^20
  iterations slows guessing. The passphrase is a transport secret shared by every node
  installed from that medium. It is handled like `/etc/shadow` on the build host (0600 file in
  a 0700 directory, `~/.cache/river-build/secrets/models-passphrase`), is never written to
  the medium, the repository or the node, and on the live system exists only in a 0600 file
  on tmpfs that the install step removes.
- **Not covered.** The payload does not authenticate the installer that opens it. That is
  the job of the release signature on the whole ISO ([RELEASE-SIGNING.md](RELEASE-SIGNING.md));
  a medium someone could modify can also carry a modified installer.

## Format (`river-modelpack` version 1)

`MANIFEST` is line-oriented; unknown lines are an error:

```
river-modelpack 1
kdf pbkdf2-sha256 <iterations> <salt, 32 hex>
aead aes-256-gcm 4194304 <nonce prefix, 14 hex>
compression zstd
lock-sha256 <sha256 of the models.lock bytes>
content <files> <bytes>
part models.rmp.000 <size> <sha256>
part models.rmp.001 <size> <sha256>
...
```

The parts, concatenated in order, are a sequence of sealed chunks: each is up to 4 MiB of
plaintext plus a 16-byte tag. Chunk `i` uses the nonce `prefix ‖ uint32be(i) ‖ last` (`last`
is 1 for the final chunk, else 0) and the associated data `"river-modelpack/1\0" ‖ salt`.
The plaintext is a zstd stream of a PAX tar archive whose entries are regular files named by
the lock's `dest` column, in lock order, mode 0644, mtime 0.

## Building it

`build/local-iso.sh` does it for the server profile when `MODELS_DIR` holds the fetched set
(stage 6), and reuses an existing payload when it was built from the same lock, its parts
verify and the passphrase opens it. By hand:

```sh
build/models-fetch.sh                                   # fill ~/.cache/river-build/models
( umask 077; mkdir -p ~/.cache/river-build/secrets
  river-modelpack genpass > ~/.cache/river-build/secrets/models-passphrase )
river-modelpack pack --lock models.lock --models-dir ~/.cache/river-build/models \
    --out ~/.cache/river-build/local-iso/model-payload/river-models \
    --passphrase-file ~/.cache/river-build/secrets/models-passphrase
river-modelpack check --payload .../river-models --passphrase-file ...   # parts + passphrase
```

`build/iso-root-stage.sh` adds the directory to the finished ISO with `xorriso -indev <iso>
-outdev <new iso> -boot_image any replay -map <payload> /river-models`, which keeps the boot
records (El Torito, the hybrid MBR and the appended EFI partition) and the volume label.
The payload is never in the live rootfs, so it costs the live system no RAM and
`20-clone-rootfs` never copies it.

## Installing from it

Step `72-models-payload` (server installer, after `50-runink-user`) finds `/river-models` on
the boot medium, creates `<pool>/models` (`mountpoint=/var/lib/core/models/shared`,
`recordsize=1M`, `compression=off`, `atime=off`, not auto-snapshotted, encryption inherited)
and unpacks into it:

- `runink-install` asks for the passphrase with echo off, up to three times. A blank answer
  defers the models: nothing is written and enrollment can still sync them.
- `runink-autoinstall --models-passphrase-file FILE` reads it from a file (keep the file on
  tmpfs). Without the option an unattended install defers the models.
- A pool that already has `<pool>/models` (re-install into an imported pool) is verified
  against the lock and kept; a mismatch stops the step and leaves the dataset untouched.
- Afterwards: `river-modelpack verify --dir /var/lib/core/models/shared --lock
  /usr/local/share/runink/models.lock` re-checks the set on the node at any time.

## Size

Measured on 2026-09-24 for the 29 files `models.lock` then pinned (coder/general, stt, embedding,
vision and five piper voices). The embedding row (146,146,432 bytes) has since been removed:
the tier is pending re-selection for a model mistral.rs serves, so the current set is 28 files,
about 146 MB smaller than the table below:

| | bytes | GiB |
|---|---:|---:|
| Model set (plaintext) | 19,902,270,074 | 18.53 |
| Payload (9 parts: 8 × 1,992,294,400 + 1,542,450,138) | 17,480,805,338 | 16.28 |

zstd saves 12.2% overall, almost all of it on the Voxtral bf16 safetensors (about 76% of its
size at level 12); the Q4_K_M GGUFs are nearly incompressible (97-100%), the piper voices
compress to about 43%. Packing takes about 5 minutes on 6 threads; unpacking is bound by
the medium's read speed (about 17.5 GB to read).

Budget: the server ISO is the base image plus 16.3 GiB. A 233 GB stick holds it, the
workstation ISO and a large data partition ([USB-MULTIBOOT.md](USB-MULTIBOOT.md)). Each part
stays below 2 GiB, so a release can mirror the payload as ordinary release assets; the
per-file model mirror of `build/models-fetch.sh` (`RIVER_MODELS_MIRROR`, whole files or
`.partNNN` pieces) is unchanged. An ISO with the payload is larger than a single 2 GiB
release asset; publish it as split parts, or publish the base ISO and the payload parts
separately.
